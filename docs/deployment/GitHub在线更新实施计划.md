# GitHub 在线更新实施计划

日期：2026-10-11。状态：计划待实施；本轮没有修改 Android 代码、升级版本、配置 Secrets、创建发布工作流或推送 GitHub。

2026-10-12：用户批准开始实施。以上为计划制定时的基线，实际执行状态见 [实施与验收记录](../qa/github-update-2026-10-12.md)，操作见 [GitHub 在线更新操作](GitHub在线更新操作.md)。云端签名凭据导入仍需要单独授权。

## 1. 目标与边界

在现有 App 内实现“检查更新 → 显示版本和说明 → 点击更新 → 下载并校验 → 系统确认覆盖安装”。手机不需要登录 GitHub，也不需要自行寻找安装包。普通 Android 应用仍需用户确认安装，不承诺静默升级。

默认更新源改为现有公开仓库 `zhixiao113/AIQuizLite-AS`。学校虚拟机、Nginx、公网 IP、域名和内网穿透不再是在线更新的必要条件；不连接或修改学校服务器。手机必须能访问 GitHub 的清单和安装包下载域名，先做目标网络验证，不承诺所有网络都可用。

保留本地 BAT、Python 更新服务、原证书构建脚本及 [本地更新方法](../本地更新方法.md)。不删除旧 Release、不换签名、不卸载已有应用，不扩展到其他刷题业务重构。

当前基线：提交 `18054a4`，正式包 1.1.2/code13；原 `app_sign.jks/key0`；包名 `com.example.aiquizlite`。已有 APK 下载、哈希、包名/版本/签名比较和安装确认界面，但更新源仍为旧 SakuraFrp 地址，并存在全信任 TLS 逻辑。

## 2. 选定的架构

```text
受信任代码 → Actions 测试/lint/构建/原证书签名
                      ↓
             Release 上传并公开下载核验
                      ↓
             切换 stable 更新清单（最后一步）
                      ↓
手机读取清单 → 固定版本 APK 下载 → 校验 → 用户确认安装
```

这是本项目拟实现的设计，不是 GitHub 自带的手机升级功能。

- APK：放在带版本 tag 的 GitHub Release，使用固定版本下载地址。已发布的 tag/同名 APK 不覆盖，升级必须使用新的 code/tag。
- 清单：拟建立只存发布元数据的 `update-channel` 分支，手机读取其 `stable.json`；正式源候选地址为 `https://raw.githubusercontent.com/zhixiao113/AIQuizLite-AS/update-channel/stable.json`。该地址目前尚未创建。
- 不把 GitHub “latest Release”当作手机唯一发布指针。上传、发布候选包不等于允许所有手机更新；只有通过检查并切换 stable 清单才生效。
- stable 清单包含固定 tag 的完整 APK URL，不使用会随“latest”变化的 APK URL，避免清单与 APK 跨版本错配。
- 清单分支同时保存 `previous.json`、版本最高使用记录及发布审计记录。回滚不降低版本最高使用记录，防止重复使用已发过的 code。
- 发布与回滚使用同一并发组，禁止中断正在执行的切换。写清单前核对远程分支实际提交，竞争时拒绝覆盖；不依赖任务恰好按版本顺序执行。
- GitHub 原始文件/CDN 可能有缓存；验证需允许有限重试和传播等待，不能把暂时旧内容当成部署损坏，也不能承诺回滚瞬间对所有手机生效。

## 3. 清单与客户端规则

GitHub 清单拟包含：`schemaVersion`、`packageName`、`versionCode`、`versionName`、`apkUrl`、`apkSha256`、`apkSize`、`signerSha256`、`notes`、`releaseTag`、`sourceCommit`、`publicationId`、`releasedAt`。只存公开发布信息，不存密钥、密码或 Token。

新客户端区分更新源和下载地址，不再把所有 APK 地址机械拼接成“清单目录 + apkFile”。本地源继续兼容现有 `version.json + apkFile`，不能以新字段破坏 BAT 产物。

客户端验收规则：

1. GitHub 为默认源；保留“本地备用源”的明确入口，显示当前选择。源切换必须由用户操作，不在失败时悄悄转入旧的宽松 TLS 通道。
2. 检查更新失败显示“检查失败/网络不可达”等准确原因，不能显示“已是最新版”；只有完整合法清单且版本比较完成才能给出最新版结论。
3. 只提示比已安装 versionCode 更高的包。同 code 不提示，不允许降级。发布端同时防止同 code 重发不同二进制文件。
4. GitHub 清单与 APK 强制有效 HTTPS，移除全信任 TrustManager 和总是返回 true 的 HostnameVerifier。重定向有次数上限，逐跳校验证书、协议及已审核 GitHub/CDN 主机；拒绝 HTTPS 降级及非预期地址。
5. 旧 SakuraFrp 备用源如仍使用非系统信任证书，需可信渠道核实证书，再做仅该端点的限定信任；未完成前不能宣称备用源在新版手机端可用。桌面脚本和旧版手机更新路径仍保留，不为兼容而恢复全局信任绕过。
6. 必须校验下载大小、SHA-256、APK 实际包名、版本和原签名。不能把清单声明的签名当作新的信任根；保留安装包与已安装包的签名比较及固定发布签名检查。
7. 限制清单大小、字段和 APK 下载上限；解析非 JSON 页面、缺字段、异常 URL、截断下载、哈希或签名不符时停止安装并清理临时文件。
8. 保留下载进度和取消、失败重试、未知来源授权及系统安装确认；取消、断网、返回或 Activity 销毁不能启动安装。处理授权返回、重复点击、未知 Content-Length 和跨屏状态，避免误报成功。
9. 不把 GitHub 登录凭据放入 APK；公开清单及 APK 的手机读取不依赖发布工作流 Token，也不高频调用 Releases API。

## 4. GitHub 自动发布与凭据

分开两类工作流：

- CI：PR 和 main 代码推送执行适用的 Android lint、单元测试、Python 发布测试及构建验证、凭据扫描/依赖与外部 Action 来源检查。PR 不拿正式签名凭据，不用 `pull_request_target` 执行外来代码。
- Release：只针对受信任的 main 提交，通过手动触发或受控版本 tag 构建签名并发布。起步采用手动触发/确认；验收后可启用受控 tag 自动发布。不把每次文档提交或未经验证的代码推送都变成手机更新。

版本递增由代理/发布工具负责：发版前同时提高 versionName/versionCode，核对所有已使用版本，而不是让用户手动改。版本先固定在受信任源码提交中，失败且尚未对外发布的构建可重试；已发布版本不能覆盖。CI 不用运行次数临时改出一个与源码不一致的 APK 版本，也不自动提交引发无限发版循环。

受保护的 `production` Environment 拟存：

- `AIQUIZ_RELEASE_KEYSTORE_BASE64`：原证书库的编码内容，Base64 不是加密，必须作为 Secret 保存；先检查大小是否符合 Secret 限制。
- `AIQUIZ_RELEASE_STORE_PASSWORD`、`AIQUIZ_RELEASE_KEY_PASSWORD`：两项独立签名密码。
- `AIQUIZ_RELEASE_KEY_ALIAS=key0` 可作为普通变量；发布证书 SHA-256 为公开固定值。

本机 DPAPI 文件不能直接供 Linux runner 解密。云端导入原密钥必须另行得到用户明确授权；本轮不上传。Secrets 未配置前先完成本机签名包发布链路，不能换密钥或关闭签名检查来让 CI 通过。

CI 在 GitHub 托管 Linux runner 执行，不占用学校 ARM 虚拟机。签名文件只在受信任签名任务的临时目录还原，通过临时环境变量提供密码，任务结束清理；不加入仓库、缓存、APK、日志或构建附件。外部 Actions 固定审核过的提交版本。

当前 `app/build.gradle` 的 Debug 也引用正式签名，不能原样搬进不带 Secrets 的 PR 构建。实施时明确区分无私钥的测试编译/不签名构建与正式签名 Release；前者绝不作为手机更新产物发布，后者缺少原密钥或凭据必须直接失败，不自动回退 Debug/新密钥。

工作流默认 `contents: read`，发布/回滚任务才需要 `contents: write`；优先使用短期 `GITHUB_TOKEN`。配置 Actions、production Environment、清单分支保护及审批需要对应管理权限，实施时先核实保护规则允许预期自动写入，不为方便而关闭 main 保护。单人维护时不得设置无法满足的审批组合。

## 5. 发布顺序、失败与回滚

### 正常发布

1. 固定源码 commit/tag 与新版本，检查最高已用 code、Secrets/权限、发布并发状态。
2. 执行 CI 门禁并用原证书构建 Release；失败直接停止，stable 清单不变。
3. 验证 APK 实际包名、版本、签名、大小、哈希，生成该版清单；创建草稿 Release 并上传。
4. 验证上传结果；公开候选 Release 后从公开下载链接重新取得 APK，校验内容。候选尚未写入 stable，手机不会因此自动收到更新；公开候选并非保密灰度。
5. 在切换前保存上一份 stable 及其对应文件；一次清单提交写入新的 stable、previous 与审计状态。APK 先可用，指针最后更新。
6. 复核远程提交、公开清单和固定版本 APK 可用性。允许缓存传播重试；确认成功后更新 Release 展示状态和发布摘要。

### 失败及恢复

| 失败位置 | 处理 |
| --- | --- |
| 测试、构建、签名或上传失败 | 终止发布，stable 不变；保留失败报告，不把不完整包推广。 |
| 公开 APK 下载/校验失败 | 不切换 stable；标记候选失败，保留日志并检查或重试，不能覆盖已发布同版本包。 |
| 切换结果不确定 | 读取远程真实提交确认是否成功；不能因请求超时就盲目覆盖或撤回其他版本。 |
| 已切换后确认健康检查失败 | 仅当指针仍属于本次发布时，新增恢复提交重新指向已验证 previous；不强推清单分支、不覆盖更晚发布。复核恢复结果。 |
| 正常发布后发现应用 bug | 手动“撤回/回滚发布指针”，阻止后续设备获取问题版本，再发更高 code 的修复包。 |
| GitHub 本身不可用 | 不宣称回滚成功；当前 App 保持可用，报告失败。GitHub 恢复后核对实际发布状态。 |

当前版、上一成功版及已有历史 Release 均保留；本阶段不自动删除历史 APK，也不删除在途下载依赖的链接。回滚的文件清单来自已经核验的历史版本，不接受任意网址或任意代码执行输入。

已经升级的手机不会因清单回退而自动降级。回滚只能撤回发布入口，不能保证所有设备免于一次应用 bug；完整防护仍需测试和目标手机验收。版本最高使用记录在回滚时保留，修复版本必须大于已用最高 code。

### 日志

Actions 保存成功与失败摘要、测试/lint/签名校验结果，失败时上传脱敏报告；建议保留 90 天，但须核对仓库实际保留设置。清单分支保留精简公开发布审计：时间、commit、tag、版本、哈希、步骤、结果、previous、恢复结果及 run 链接，不上传完整私密日志。下载 APK 本身不依赖这些 Actions 附件。

自动恢复失败也必须单独记录并让工作流保持失败状态；不能把“尝试回滚”写成“恢复完成”。基础版本与发布审计保留在 Git/Release，Actions 临时日志过期不影响回滚定位。

## 6. 实施阶段与交付

| 阶段 | 工作 | 完成条件 |
| --- | --- | --- |
| P0：可达性与准备 | 目标手机 Wi-Fi/移动网络测试 GitHub 清单候选域名及现有 APK；核实权限、Secrets 授权 | 真实手机能取得文件；确认云签名授权策略。若失败，先调整公开下载源，不继续宣称可用。 |
| P1：协议与客户端 | 拆分源/清单/下载 URL；兼容本地协议；TLS、重定向、错误处理及测试 | 客户端安全/兼容测试通过，更新弹窗、取消和安装路径不回归。 |
| P2：发布与回滚工具 | 清单生成/校验、Release 草稿上传、公开下载核验、原子指针切换、日志和恢复 | 沙箱/测试通道故障注入证明失败不破坏 stable，回滚不影响更晚版本。 |
| P3：Actions 配置 | CI、受信任发布、手动回滚；最小权限、并发控制、生产环境 Secrets | Actions 真正运行通过；模拟签名/上传失败和恢复失败都有可追踪结果。 |
| P4：过渡包 | 代理主动提高版本、原证书 Release 构建，同步本地更新和 GitHub APK | 拟为 1.1.3/code14；若期间已有新版本，从实际最高版本继续递增，不硬编码复用。用户不用自行改版本或构建。 |
| P5：真机闭环 | 旧版覆盖到过渡包，再用真实更高 code 验证 GitHub App 内升级；数据与回滚验收 | 至少完成两次构建对应的升级路径，手机无需卸载、题库/进度保留；不能用网络 mock 代替真机闭环。 |

过渡包通过仍保留的本地在线更新送达；若旧通道不可达，用户只需手动下载并覆盖安装这一次，不能让仍指向旧地址的 code13 自行发现 GitHub。过渡后的新包默认读取 GitHub 清单。

闭环演练的第二个包拟为 1.1.4/code15（以届时真实最高版本为准），说明为更新链路验收，不夹带新业务功能。其正式清单切换在约定验收窗口执行，仍受发布门禁控制；本轮不生成这两个包。若安装后的包需修复，使用更高 code，不能同 code 重打替换。

## 7. 验收清单

- GitHub 发布及正常使用不需要学校虚拟机、公网 IP、域名、穿透或手机 GitHub Token。
- 全新安装、code13 → 过渡包、过渡包 → 更高 code 包均用同一原证书；题库、图片、错题、收藏、进度、专项练习草稿及用户设置保留。
- 没有新版本、存在新版本、清单缺失/非法、HTML 响应、超时、断网、校验不符、错误包名/签名/版本、取消和重复操作都有正确状态。
- 合法 GitHub HTTPS 重定向可用；不可信证书、异常主机和协议降级均拒绝。GitHub 不可达不会悄悄绕过证书或误报最新。
- 同版本上传冲突、旧/乱序任务、并发发布、切换中断、上传失败、公开下载失败、指针竞争、回滚失败均有故障注入测试及日志。
- 回滚后未升级设备不再收到被撤回版本；已升级设备不自动降级，修复包版本继续提高。
- 本地 BAT、构建脚本和 `version.json + apkFile` 不回归；若新版手机仍需旧 FRP 备用入口，必须另验其端点信任配置，不能只以脚本仍存在判定通过。
- 保留既有 153 项 Android 测试和 10 项发布器测试，新增测试后报告实际数量；Release lint 0 错误。既有 112 条警告需列出基线并记录变化，不伪称零警告。
- 公网下载哈希、签名和版本核对通过；手机 Wi-Fi/移动网络、安装授权、取消及数据保留需用户目标手机验证。自动检查不等于真机已完成。

## 8. 仍需确认的事项

1. 目标手机是否能在日常网络下载现有 GitHub APK并访问原始文件域名。若不能，需用户选择另一个公开下载源；不自行启用第三方 GitHub 代理。
2. 是否授权将原签名文件与两项密码放入受保护的 GitHub Environment Secrets，以完成全云端签名。无需再次在聊天发送密码；授权前可先用本机签名包验证发布链路。
3. 首次正式发布的触发/审批方式，以及上述两次真机升级的验收时间。实施建议先手动触发，稳定后受控版本 tag 自动运行。
4. 是否要求新版手机继续使用旧 FRP 备用地址；如果需要，核验旧端点证书方案。保留本地脚本是确定要求，但不等于允许继续使用全信任 TLS。
